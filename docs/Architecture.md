# Архитектура бэкенда Gloso: первый этап

Обновлено: 19 ноября 2026 г. Документ фиксирует согласованный объём разработки и технические контракты для реализации с нуля. Вся серверная логика размещается в чистой директории `backend/`. Начальный рынок — автосервисы.

**Состояние реализации:** в `backend/` реализован локальный MVP: административный API, допуск и учёт минут, слоты и бронирование, Relay/SMS, аудит, восстановление и очистка. Реальные провайдеры (Google Calendar, SMSAPI, Zadarma, ElevenLabs) ещё не подключены; используются PostgreSQL и mock-адаптеры. Production-запуск заблокирован до проверки реальных контрактов. Запуск и ограничения — в [`backend/README.md`](../backend/README.md), фактические локальные контракты — в [`backend/API.md`](../backend/API.md), схема БД — в [`Database.md`](Database.md).

Условия оказания услуги описываются в [`regulamin.html`](../regulamin.html) (версия 1.2 от 19.11.2026); при расхождении с индивидуальным договором приоритет имеет договор. Юридические черновики не являются перечнем функций текущего этапа. Схемы и их актуальные пояснения — в [`Architecture Scheme.md`](Architecture%20Scheme.md).

## 1. Объём и текущее состояние

### Входит в первый этап

- Создание новых записей в Google Calendar — **Tryb Kalendarza**.
- Передача заявки без бронирования — **Tryb Zgłoszeniowy / Relay**, в том числе при недоступности календаря.
- Административный API для настройки мастерских; без административного интерфейса.
- Для каждой мастерской: отдельный номер назначения Zadarma, отдельный агент ElevenLabs, не более одного подключённого календаря и один сотрудник — получатель SMS.
- Полная длительность выбранной услуги; пока фиктивные услуги, длительности и расписания. Неизвестная услуга направляется на диагностику по настройкам мастерской.
- Пилот: 14 календарных дней, первоначальный лимит **40 минут AI**. После исчерпания — запрет новых AI-разговоров, без принудительного прерывания текущего.
- В PostgreSQL сохраняются настройки мастерских, услуг и расписаний, связи с номером/агентом/календарём, состояние пилота, расход минут и минимальные технические сведения для защиты от повторных операций. Обезличенные зашифрованные аудиты звонков хранятся **30 дней**. Аудио, транскрипции, заявки и персональные данные визитов в БД не сохраняются.

### Отложено

- Поиск существующих визитов для звонящего, переносы, отмены и SMS-коды. При будущем добавлении изменять можно только события, созданные Gloso, не ручные записи мастера.
- Платные периоды, начисления, дополнительные пакеты, автоматическая сверка платежей и банковские интеграции. Будущую оплату подтверждает администратор вручную.
- SMS клиентам, напоминания, несколько получателей, e-mail и WhatsApp.
- Несколько календарей/исполнителей/постов, OAuth-подключение календаря, интерфейс управления Relay-заявками.
- Хранение и просмотр записей разговоров или транскрипций в бэкенде.

### Что уже есть

ElevenLabs есть, но настройка отдельных агентов и инструментов ещё требует проверки. Номера Zadarma и SIP trunk отсутствуют; SMSAPI не настроен; Northflank и Neon не созданы. Локальный MVP использует PostgreSQL и тестовые адаптеры. Реальных примеров webhook и tool call пока нет: нельзя считать их поля и способы корреляции подтверждёнными. Обычные mock Calendar/SMS хранятся в памяти; их долговечность при перезапуске не предполагается. Для проверки падений отдельный тестовый провайдер работает вне процесса бэкенда.

## 2. Стек и слои

| Область            | Решение                                                                                               |
| ------------------ | ----------------------------------------------------------------------------------------------------- |
| Телефония и голос  | Zadarma + ElevenLabs Conversational AI (LLM из одобренного в DPA списка: OpenAI / Anthropic / Google) |
| HTTP API           | Node.js + TypeScript + Express                                                                        |
| Валидация и доступ | Zod + проверка секретного заголовка                                                                   |
| БД и ORM           | PostgreSQL + Drizzle; сейчас локально, позднее Neon (ЕЭЗ)                                             |
| Календарь          | Google Calendar через адаптер, доступ служебного аккаунта                                             |
| Уведомления        | smsapi.pl через адаптер                                                                               |
| Хостинг            | Сейчас локально; позднее Northflank                                                                   |

Бэкенд обрабатывает инструменты и события, а не передаёт аудиопоток. При прямой SIP-интеграции аудио проходит между Zadarma и ElevenLabs.

1. **API Layer:** маршруты, проверка секретных заголовков, Zod, контроллеры, обработка ошибок. Административные и агентские полномочия разделены; секреты не передаются в промптах и не записываются в логи.
2. **Business Logic Layer:** Tenant Resolver, нормализация дат, Slot Calculation Engine, Booking Manager, обработчик Relay, проверка допуска по лимиту пилота.
3. **Data Access Layer:** Drizzle, конфигурация мастерских, состояние пилота и минут, технические сведения для защиты от повторов и зашифрованные обезличенные аудиты. Заявки и тела webhook не сохраняются.
4. **Infrastructure Layer:** Calendar Adapter, SMS Adapter и адаптер событий телефонии/ElevenLabs. Тестовые реализации заменяются реальными без изменения сценариев.

Административный API управляет режимом, номером, агентом, календарём, получателем SMS, услугами, расписанием и состоянием пилота. Он не предоставляет архив персональных данных звонящих.

## 3. Контекст мастерской и безопасность

- Режим `CALENDAR` или `RELAY` задаётся администратором. Ошибка календаря включает Relay только для текущего обращения, не меняя постоянную настройку мастерской.
- Tenant Resolver сопоставляет доверенный номер назначения и агента с мастерской. `workshop_id`, переданный моделью, не является источником полномочий.
- Внутренний `call_id`, идентификатор Zadarma и `conversation_id` ElevenLabs — разные сущности. Связь устанавливается по проверенным серверным метаданным; конкретный механизм проверяется после получения реальных событий.
- Секретный заголовок защищает tool endpoints, но не доказывает принадлежность произвольного идентификатора звонка. Для webhook провайдера используется поддерживаемая им серверная аутентификация и защита от повторов; нельзя предполагать наличие пользовательского заголовка у каждого провайдера.
- Zod проверяет форму и ограничения данных; принадлежность слота мастерской, режим, расписание и допустимость операции проверяются бизнес-логикой.
- Телефон из доверенного контекста нормализуется в E.164, но Caller ID не является доказательством владения номером. Модель не может незаметно заменить его продиктованным номером.
- При скрытом Caller ID допускается Relay-заявка с продиктованным номером, помеченным **непроверенным**. Без номера для обратной связи нельзя сообщать об успешном сборе всех обязательных данных. Доступ к существующим броням не предоставляется.
- Утверждать успешную запись или отправку уведомления можно только по результату соответствующего адаптера. Тестовые ответы не выдаются за реальные интеграции.

## 4. Общие правила звонка и услуг

1. Сохраняется требование подключать AI не раньше чем через **10 секунд от начала исходного вызова**, в том числе при занятой линии и после закрытия. Механизм и доступность времени исходного вызова ещё нужно проверить в Zadarma/SIP.
2. До запуска нового AI-разговора проверяются активность пилота и доступный лимит. Это должно происходить до подключения ElevenLabs, а не только при первом tool call.
3. В начале AI-разговора воспроизводится согласованный информационный аудиокоммуникат. Необслуживаемый запрос/спам может завершать разговор, но уже использованное время AI учитывается.
4. Обязательные данные: **имя, телефон, марка/модель автомобиля, описание проблемы, предпочтительное время**. Фамилия и регистрационный номер не являются обязательными.
5. Длительность слота равна полной длительности выбранной услуги из конфигурации, а не единому «буферу 60 минут на авто». Услуга диагностики также имеет настроенную длительность.
6. Фиктивные рабочие часы, длительности и правила поиска слотов — тестовые данные, а не обещание клиентам. Фиксированный шаг, буферы, горизонт и минимальный срок записи пока не согласованы; их нельзя незаметно зашивать как бизнес-правила.

## 5. Сценарий Calendar

Один рабочий Google Calendar мастерской является источником занятости. Мастер вручную предоставляет служебному аккаунту доступ на чтение и создание событий. Backend использует Service Account; пользовательский OAuth-процесс не нужен. Краткоживущие токены Google всё равно обновляются библиотекой авторизации, а ключ хранится вне репозитория.

1. AI выясняет услугу и желаемое время. Для неизвестной услуги предлагает диагностику согласно конфигурации мастерской, не выдумывая длительность или цену.
2. Backend нормализует относительную дату **до запроса занятости** в `Europe/Warsaw`. Неоднозначные даты уточняются; прошлые и несуществующие локальные часы при переводе времени не предлагаются.
3. Calendar Adapter получает занятость, включая ручные записи мастера. Slot Calculation Engine учитывает её, рабочие часы и полную длительность услуги.
4. Возвращаются конкретные варианты с `start_at`, `end_at` и защищённой от подмены ссылкой на слот, ограниченной мастерской и выбранной услугой. Не требуется таблица персональных бронирований в PostgreSQL.
5. После явного выбора клиентом Booking Manager проверяет тот же слот повторно. При конфликте предлагает другой вариант; повторно интерпретировать «завтра» при создании нельзя.
6. Создаётся событие в Google Calendar с необходимыми данными визита и техническим признаком происхождения Gloso. Эти данные не копируются в нашу БД и логи.
7. **Только после подтверждённого создания события AI подтверждает бронь.** Одному настроенному сотруднику мастерской отправляется SMS. Ошибка SMS не отменяет событие и не является поводом создать второе.

Защита от параллельных записей Gloso, повторных tool calls и восстановление после неопределённого ответа Google строятся на постоянном журнале операций и межпроцессном шлюзе бронирования мастерской. Шлюз нашего сервиса не блокирует ручные изменения Google Calendar; абсолютная защита от конфликтов с ними не гарантируется. Ограничения хранения разобраны в разделе 10.

#### Технические требования к `slot_id` и конкурентности

- **Формат `slot_id`:** stateless-токен, подписанный HMAC-SHA256 (секрет из env), кодированный в base64url. Внутри payload: `tenant_id`, `service_id`, `start_at` (ISO 8601), `end_at` (ISO 8601) и `exp` (TTL 15 минут). Таблица предложенных слотов в БД не создаётся. При бронировании Booking Manager проверяет подпись, срок действия и соответствие `tenant_id` текущему контексту звонка.
- **Защита от гонок (Concurrency):** `pg_advisory_xact_lock(hashtext(tenant_id))` используется только в коротких транзакциях для согласованного изменения журнала и `tenant_booking_gates`. Между транзакциями одна мастерская может иметь только одну незавершённую операцию бронирования. Постоянный шлюз охватывает повторную проверку занятости, создание события и фиксацию/сверку результата; он действует между экземплярами приложения и после перезапуска. Одна транзакционная блокировка, отпущенная до запроса Google, этого не обеспечивает.
- **Защита от дублей (Idempotency):** сервер вычисляет ключ бронирования как HMAC от канонических `tenant_id`, внутреннего `call_id`, действия, `service_id`, `start_at`, `end_at`. Строка `slot_id` и её `exp` в ключ не входят: повторная выдача того же слота не создаёт новую операцию. Исходные время визита и токен в БД не сохраняются. Для Relay используется серверный идентификатор логической операции, привязанный к звонку; тексты заявки и их хеши не используются как ключи. Повтор возвращает зафиксированный технический результат, а не запускает внешнее действие заново.
- **Истёкший токен:** после проверки подписи и контекста разрешён только поиск уже существующей операции и возврат её результата/статуса. Начать или повторно отправить создание по истёкшему токену нельзя. Для продолжения нужны действительный токен с теми же стабильными полями и повторная валидация. При изменении расписания или услуги проверяются актуальные ограничения.

#### Журнал бронирования, внешние вызовы и восстановление

1. **Транзакция 1:** взять advisory lock мастерской, проверить `processed_events` и её шлюз. Для `COMPLETED` или `FAILED` вернуть сохранённый технический результат без повторного выполнения. Для `PENDING`/`UNCERTAIN` не создавать вторую операцию: действующий владелец продолжает работу, остальные получают `PENDING_VERIFICATION`; после потери владельца запускается восстановление. Если другой незавершённый запрос занимает шлюз, новую бронь не начинать. Для новой операции записать `PENDING`, заранее вычисленный совместимый с Google `external_ref`, ссылку на исходный календарь и владение шлюзом. **Закоммитить всё до внешних вызовов.**
2. **Вне транзакции БД:** владелец повторно читает занятость и проверяет слот, затем вызывает `events.insert` с `id = external_ref`. При конфликте до создания фиксируется `FAILED` с кодом `SLOT_CONFLICT`. Сетевые запросы имеют ограниченные тайм-ауты; транзакция PostgreSQL не удерживается во время ожидания провайдера.
3. **Транзакция 2:** подтверждённое создание переводит операцию в `COMPLETED`; подтверждённый отказ без создания — в `FAILED`. Шлюз освобождается только при определённом исходе, с проверкой владельца и версии владения. При сетевом тайм-ауте или неоднозначном ответе фиксируется `UNCERTAIN`, шлюз остаётся занят. Если транзакция 2 не выполнилась, оставшийся `PENDING` также требует сверки.
4. **Сверка:** восстановитель получает исключительное владение операцией и вызывает `events.get(external_ref)` в исходном календаре. Найденное событие проверяется на соответствие операции и позволяет зафиксировать `COMPLETED`. Тайм-аут сверки не означает отсутствия события. `404` не доказывает завершения ранее отправленного `insert`: при допустимом повторе используется **только прежний ID**, а `409` ведёт к повторной сверке, не к генерации нового ID. Новый `insert` также требует доступных валидированных данных запроса и действительного слота; персональные данные не восстанавливаются из БД.
5. **Потеря владельца:** lease определяет, кто может восстанавливать операцию, но его истечение не освобождает шлюз для другой брони и само по себе не останавливает старый запрос Google. Версия владения защищает изменения БД, но не является fencing-механизмом Google Calendar. До доказанного завершения/прекращения старого внешнего действия шлюз не освобождается, в том числе после единичного `404`. Если безопасно установить исход невозможно, мастерская остаётся заблокированной для новых Calendar-бронирований до ручной сверки; безопасность важнее автоматического продолжения.

Классификация ошибок определяется контрактом Calendar Adapter: произвольный `5xx`, разрыв соединения или `409` нельзя автоматически считать гарантией отсутствия создания. Автоматический восстановитель без персональных данных может сверять событие по ID, но не обещает восстановить и отправить потерянное тело заявки. SMS выполняется отдельной операцией по разделу 7.

## 6. Сценарий Relay и отказ календаря

### Бумажный учёт / настроенный Relay

1. AI собирает обязательные данные и предпочтительное время. Дата может быть нормализована для сообщения, но остаётся пожеланием, не свободным слотом.
2. Backend формирует SMS одному настроенному сотруднику и передаёт его SMS Adapter. Заявка обрабатывается без записи её содержимого в PostgreSQL.
3. Клиент слышит, что обращение передано, а время требует подтверждения мастером. При ошибке передачи нельзя обещать, что мастер уже получил заявку; принятие SMS провайдером и доставка различаются.
4. Мастер сам проверяет бумажное расписание, связывается с клиентом и фиксирует договорённость. Дальнейшая работа проходит **вне системы**.

В Relay не вызывается расчёт доступности, не создаётся событие и не используется теневой календарь.

### Календарь недоступен

AI сообщает, что сейчас не может подтвердить запись, и использует Relay для этого обращения. Постоянный режим мастерской остаётся `CALENDAR`.

Если ошибка возникла при чтении занятости и создание ещё не запускалось, можно сразу передавать Relay-заявку. Если запрос создания завершился тайм-аутом, событие могло быть создано: сначала требуется сверка результата. До неё нельзя обещать ни подтверждённую бронь, ни гарантированное отсутствие записи; нельзя создавать повторное событие или выдавать SMS за подтверждение визита.

## 7. SMS и внешние ошибки

- Единственный канал — **smsapi.pl**, единственный адресат — один настроенный сотрудник мастерской. Подпись отправителя ещё предстоит настроить; имя `Gloso` не считается уже зарегистрированным.
- SMS о Calendar-записи содержит подтверждённые данные; Relay-SMS явно обозначает просьбу о контакте и неподтверждённое время. Непроверенный телефон помечается отдельно.
- В текущем этапе нет SMS звонящему, кодов проверки, напоминаний, e-mail и WhatsApp.
- Backend не архивирует текст SMS или заявки в БД. Адаптер возвращает результат принятия/ошибки; фактическая доставка — отдельный статус провайдера.
- Ограниченные повторы и обработка неопределённых ответов должны учитывать риск дублей. Долговечная очередь с текстом SMS в PostgreSQL **не согласована** и противоречила бы текущему ограничению хранения.
- Отправка SMS имеет отдельную запись `processed_events`, связанную с логической операцией бронирования или Relay, и собственные `PENDING`/`COMPLETED`/`UNCERTAIN`/`FAILED`. Подтверждённое принятие сообщения провайдером не повторяется при повторном tool call. Неизвестный исход сначала сверяется, если провайдер поддерживает такую возможность. Без подтверждённой идемпотентности/сверки слепой повтор запрещён: одновременно гарантировать отсутствие дублей и доставку после любого сбоя нельзя.
- После перезапуска Relay нельзя автоматически отправить заново из БД: текста заявки там нет. Для безопасного продолжения нужны повторно полученные данные и определённый исход предыдущей попытки. Неопределённый результат обозначается `PENDING_VERIFICATION`, а не успешной передачей или гарантированным отказом. Неотправленное уведомление о Calendar-брони не отменяет созданное событие.
- Не все ошибки возвращаются как HTTP 200: ошибки аутентификации и валидации отделены от управляемых бизнес-результатов. Точные ответы tools/webhook зависят от проверенных контрактов провайдеров.

## 8. Пилот и минуты

- Первоначальные параметры: **14 дней с активации, 40 минут AI на мастерскую**. Нет автоматического перехода к платной услуге.
- Сохраняется правило учёта `ceil(ai_seconds / 60)` на разговор, включая прерванные, ошибочные и спам-звонки, если AI подключался. Начальные 10 секунд ожидания не учитываются. Длительность берётся из проверенных серверных событий, не из слов модели.
- При исчерпании лимита или окончании пилота **новые AI-разговоры не запускаются**. Уже начатый разговор не прерывается из-за исчерпания минут. Поэтому 40 минут — порог допуска, а не гарантированный жёсткий предел фактического расхода.
- Окончательное списание должно быть защищено от повторной доставки события. Счётчик и технические сведения для дедупликации хранятся в PostgreSQL. Поздние события и параллельные разговоры могут привести к превышению.
- Резерв привязывается к конкретному звонку в `active_call_reservations`, а не хранится общим изменяемым счётчиком. Активны только записи со статусом `ACTIVE` и `reservation_expires_at > now()`. Свободный лимит равен `minutes_limit - minutes_used - SUM(reserved_minutes активных записей)`; пустая сумма считается нулём (`COALESCE`). Размер резерва — тестовый `TEST_RESERVE_MINUTES` (положительное целое, по умолчанию 1), TTL — тестовый `TEST_CALL_RESERVATION_TTL_SECONDS` (по умолчанию 600). Максимальная длительность разговора 3–4 минуты пока не является подтверждённым техническим ограничением; TTL не доказывает завершения звонка.
- Допуск выполняется в транзакции с `SELECT ... FOR UPDATE` строки `pilot_usage`: проверить активность мастерской, состояние пилота, существующую запись звонка и условие `minutes_used + SUM(активных резервов) + reserve_amount <= minutes_limit`; затем создать резерв. Все допускающие и списывающие обработчики используют одну блокировку мастерской. Пространство ключа звонка — `(tenant_id, provider, external_call_id)`, где провайдер определяется доверенным адаптером.
- Повтор допуска возвращает существующее решение, не создаёт второй резерв и не продлевает TTL. Закрытый или просроченный допуск не запускает новую AI-сессию под прежним ID. Неактивный/просроченный резерв перестаёт учитываться немедленно по условию запроса, независимо от работы очистки.
- Завершение в одной транзакции закрывает резерв конкретного звонка и однократно прибавляет `ceil(ai_seconds / 60)` к расходу. Событие с `ai_seconds = 0` закрывает резерв без списания. Позднее завершение учитывается и после истечения десятиминутного TTL; отсутствие резерва не позволяет уменьшать резервы других звонков. Проверенное завершение без записи допуска учитывается отдельной дедуплицируемой записью и отмечается как техническая аномалия.
- Если завершение не пришло, освобождается только резерв; нулевая фактическая стоимость разговора не предполагается. Операционная запись звонка сохраняется 7 дней от первого принятого события, без продления повторными доставками. Для автоматической обработки требуется `now() < call_started_at + 7 days`: одного свежего времени завершения недостаточно для повторного открытия старого звонка. События вне этого окна не списываются автоматически и требуют отдельной сверки. ProviderAuthAdapter обязан проверять возраст/повторы событий; после удаления ключей семидневная дедупликация сама по себе не защищает от старого replay. В локальном протоколе для этого передаются проверяемые временные метки событий; реальный механизм подтверждается на провайдерах.
- Аварийный маршрут без AI, выдержка 10 секунд и передача Caller ID мастеру требуют проверки телефонии. Запрет нового разговора нельзя подменять отказом tool endpoint после запуска AI.
- Платные 30-дневные периоды, пакеты и банковский биллинг не реализуются. Будущее подтверждение оплаты — ручное административное действие, не интеграция с банком.

## 9. Данные, аудит и ретенция

**Аудиты звонков:** в PostgreSQL сохраняются зашифрованные технические аудиты с минимизацией данных, с целевой ретенцией **30 дней от проверенного времени завершения звонка**. Термин «обезличенный аудит» в этом документе не является гарантией полной анонимности. Это не аудиозаписи и не полные тексты разговоров. Отдельно разрешено операционное состояние из раздела 10; срок 30 дней относится к аудитам, а не автоматически ко всей БД.

Не сохраняются данные звонящих: имя, телефон и его фрагменты, автомобиль, описание проблемы, предпочтительное время визита, содержимое SMS, заявки, персональные бронирования, сырые тела webhook, аудио и транскрипции. Нельзя спрятать эти данные в зашифрованный JSON и назвать его обезличенным аудитом. Настроенные номера мастерской и сотрудника-получателя относятся к конфигурации, а не к данным звонящих.

При первом допуске генерируется случайный `audit_session_id` (UUID v4); повтор использует тот же ID. Для отклонённого допуска или завершения без допуска при необходимости создаётся отдельная техническая сессия. Связь `(tenant_id, provider, external_call_id) -> audit_session_id` хранится только в операционной записи звонка, 7 дней от её создания. В `audit_logs` внешние ID не попадают. Остальные операционные таблицы не должны создавать долговечную альтернативную связь между провайдером и аудитом.

Шифрование защищает доступ, но не делает данные анонимными. Пока существует связь, данные псевдонимизированы. После её удаления прямая связь с ID провайдера отсутствует, но UUID сессии, мастерская, временные метки, технические поля и внешние источники всё ещё могут позволять сопоставление. Поэтому утверждать «через 7 дней аудит полностью анонимен» нельзя; риск повторной идентификации оценивается отдельно, включая резервные копии.

При создании аудита устанавливается `expires_at = created_at + 30 days`. Проверенный `call-ended` до истечения срока связи обновляет аудиты сессии на `call_ended_at + 30 days`, а не на время получения webhook. Позднее создаваемые аудиты при известном завершении сразу используют этот срок; запись аудита и обработка завершения согласуются блокировкой операционной строки звонка, чтобы исключить гонку. Если завершение не пришло или связь уже истекла/удалена, сохраняется исходный срок от создания; точное приведение к завершению в таком случае не гарантируется. Просроченные записи не возвращаются пользователю и не восстанавливаются для продления срока. Истёкшая операционная связь не используется даже до её физической очистки воркером.

Любое чтение аудита фильтруется по `expires_at > now()`. Воркер в процессе приложения выполняет очистку при старте до приёма рабочих запросов и затем раз в час через `setInterval`, без перекрытия запусков. Несколько экземпляров координируют запуск очистки через БД. `DELETE FROM audit_logs WHERE expires_at <= now()` обеспечивает физическое удаление с задержкой до часа при работающем воркере; во время простоя физическое удаление откладывается до запуска. Строгий срок физического удаления независимо от доступности приложения потребовал бы отдельного планировщика. Операционные записи очищаются с учётом исключений для незавершённых операций из раздела 10.

Ключи шифрования хранятся отдельно от БД и не попадают в репозиторий/логи. Удаление по сроку охватывает копии и восстановление из backup: восстановление не должно возвращать просроченные аудиты. Обезличенный аудит подтверждает только зафиксированные технические действия, не точное содержание разговора.

Персональные данные обрабатываются временно для текущей операции; в Calendar они передаются в календарь мастерской, в Relay — в SMSAPI и получателю. Их обработка у внешних провайдеров не означает хранение в нашей БД и должна соответствовать DPA.

Backend не получает, не сохраняет и не показывает аудио/транскрипции. Предыдущее требование удаления аудио и транскрипций у голосового AI-провайдера (ElevenLabs) не позднее **72 часов** сохраняется отдельно; настройки и возможность соблюдения проверяются перед реальными звонками. При использовании LLM-провайдера по API без корпоративного режима **Zero Data Retention (ZDR)** технические логи мониторинга злоупотреблений (_abuse monitoring_) на стороне провайдера могут храниться до **30 дней**, что прямо отражено в DPA (§ 11 Регламента) и Политике конфиденциальности. Нужные технические события должны обрабатываться без журналирования и сохранения разговорного содержимого.

## 10. Постоянное операционное состояние

Уточнение от 19 ноября 2026 г.: PostgreSQL разрешено использовать для следующих данных:

1. Настройки мастерских, услуг и расписаний, включая режим и получателя SMS.
2. Связи мастерской с номером Zadarma, агентом ElevenLabs и Google Calendar.
3. Активация и состояние пилота, расход минут.
4. Минимальные технические сведения для защиты от повторных операций и списаний.
5. Обезличенные зашифрованные аудиты звонков с ретенцией 30 дней.

#### Схема таблиц PostgreSQL (Etap 1)

Персональные данные звонящих (имена, номера телефонов, авто, описания проблем, тексты SMS и заявок) в этих таблицах **строго запрещены**.

1. **`tenants`** — конфигурация мастерских:
    - `id` (uuid, PK), `name` (text), `mode` (enum: `'CALENDAR' | 'RELAY'`), `is_active` (boolean).
    - `zadarma_number` (text, unique, E.164), `elevenlabs_agent_id` (text, unique), `google_calendar_id` (text, nullable).
    - `sms_recipient_phone` (text, E.164), `work_hours` (jsonb — расписание в `Europe/Warsaw`).
    - `scheduling_config` (jsonb — **временные тестовые параметры** поиска слотов, не являющиеся финальными бизнес-правилами: `slot_step_minutes` (тест: 30), `booking_horizon_days` (тест: 14), `min_lead_time_minutes` (тест: 60)).
    - `created_at`, `updated_at` (timestamptz).

2. **`services`** — услуги мастерской:
    - `id` (uuid, PK), `tenant_id` (uuid, FK -> `tenants.id`, onDelete cascade).
    - `name` (text), `duration_minutes` (integer), `is_diagnostic` (boolean, default false — услуга по умолчанию для неизвестных запросов).

3. **`pilot_usage`** — состояние пилота и расход минут (1:1 с `tenants`):
    - `tenant_id` (uuid, PK, FK -> `tenants.id`).
    - `activated_at` (timestamptz), `expires_at` (timestamptz — `activated_at + 14 days`).
    - `minutes_limit` (integer, default 40), `minutes_used` (integer, default 0); значения неотрицательны. Поля `minutes_reserved` нет: сумма вычисляется по активным непросроченным резервам.
    - `is_blocked` (boolean, default false).

4. **`processed_events`** — защита от дублей и восстановление после таймаутов:
    - `idempotency_key` (text, PK — непрозрачный серверный ключ логической операции по правилам раздела 5, без сырых ID провайдеров, токенов слота и персональных данных).
    - `tenant_id` (uuid, FK -> `tenants.id`), `event_type` (text).
    - `status` (enum: `'PENDING' | 'COMPLETED' | 'UNCERTAIN' | 'FAILED'`).
    - `external_ref` (text, nullable — детерминированный совместимый с Google `eventId` либо технический ID SMS), `calendar_ref` (text, nullable — исходный календарь, не заменяется текущей конфигурацией при сверке).
    - `parent_operation_key` (text, nullable — связь SMS с бронью/Relay, не с аудитом).
    - `result_payload` (jsonb, nullable — строгий разрешённый список технических полей: `status`, `error_code`, `sms_status`; без времени визита, `slot_id`, контактных данных и текстов). Это не копия полного HTTP-ответа. `start_at`/`end_at` для ответа восстанавливаются из подписанного запроса или подтверждённого события Google, но не сохраняются в PostgreSQL.
    - `created_at`, `updated_at`, `expires_at` (timestamptz — окно восстановления/дедупликации 7 дней от создания, не продлевается повторным запросом).

5. **`active_call_reservations`** — допуски, индивидуальные резервы и краткоживущая связь с аудитом:
    - `tenant_id` (uuid, FK -> `tenants.id`), `provider` (text), `external_call_id` (text); составной PK по этим трём полям.
    - `audit_session_id` (uuid, случайный UUID v4), `status` (enum: `'ACTIVE' | 'CLOSED' | 'REJECTED'`), `admission_reason` (text, nullable — техническая причина решения).
    - `reserved_minutes` (integer, неотрицательный; для отклонённого допуска/завершения без допуска — 0), `reservation_expires_at` (timestamptz, nullable — для успешного допуска `created_at + 10 min` по тестовой настройке, без резерва — null).
    - `call_id` (uuid, unique — случайный внутренний ID, возвращаемый локальным допуском), `call_started_at` (timestamptz, обязательное исходное время), `call_ended_at` (timestamptz, nullable), `usage_accounted` (boolean, default false — завершение уже обработано, в том числе при нулевой длительности).
    - `booking_operation_key` (text, nullable — техническая связь с текущей/завершённой бронью звонка для запрета дубля и Relay при неопределённом исходе; без данных визита).
    - `created_at`, `expires_at` (timestamptz — операционная запись и связь удаляются через 7 дней от создания, не через 10 минут). Истёкший резерв не удаляется немедленно и не мешает позднему списанию в пределах окна.

6. **`tenant_booking_gates`** — постоянная сериализация Calendar-бронирований:
    - `tenant_id` (uuid, PK, FK -> `tenants.id`), `state` (enum: `'IDLE' | 'BUSY' | 'RECOVERY_REQUIRED'`).
    - `operation_key` (text, nullable — текущая операция `processed_events`), `owner_token` (uuid, nullable), `owner_version` (bigint), `lease_expires_at` (timestamptz, nullable), `updated_at` (timestamptz).
    - Ровно один шлюз на мастерскую; захват, смена владельца и освобождение атомарны под advisory lock. Истечение lease не означает разрешения новой операции. В таблице нет времён визитов и содержимого заявок; это не теневой календарь.

7. **`audit_logs`** — зашифрованные технические аудиты (сроки и ограничения обезличивания — раздел 9):
    - `id` (uuid, PK), `tenant_id` (uuid, FK -> `tenants.id`), `audit_session_id` (uuid). Нет FK с каскадным удалением из операционной записи звонка.
    - `action` (enum: `'CALL_ADMITTED' | 'CALL_REJECTED_LIMIT' | 'SLOTS_CHECKED' | 'BOOKING_CREATED' | 'BOOKING_CONFLICT' | 'RELAY_SENT' | 'PROVIDER_ERROR'`).
    - `encrypted_meta` (text — JSON, зашифрованный `AES-256-GCM` в формате `iv:authTag:ciphertext`, содержащий **исключительно** разрешённые технические данные: `service_id`, `mode`, `provider_status`, `ai_seconds`; **строго без `slot_start_at`, времени визита, контактных данных, текстов и внешних `call_id`**). Допустимость корреляции оценивается отдельно; шифрование не гарантирует анонимности.
    - `created_at` (timestamptz), `expires_at` (timestamptz — по правилам раздела 9: при неизвестном завершении `created_at + 30 days`, при известном — `call_ended_at + 30 days`).

Административный API сохраняет конфигурацию в PostgreSQL через Drizzle. Рабочие счётчики и дедупликация переживают перезапуск; временное состояние в памяти используется только там, где его потеря допустима, и в тестовых адаптерах. Транзакции и ограничения БД обеспечивают атомарность локальных изменений; внешние операции Google/SMSAPI требуют отдельной сверки результатов.

Очистка удаляет просроченные операционные записи и связи с аудитом. До истечения окна восстановления незавершённые бронирования сверяются. Если за 7 дней исход не установлен, мастерская переводится в `RECOVERY_REQUIRED`; связь шлюза с удаляемой операцией очищается, но сам запрет новых бронирований не снимается. Минимальное состояние блокировки без ID провайдера/события и связи со звонком остаётся до ручной проверки администратором. Очистка не должна освобождать шлюз незаметно или создавать новый `external_ref`. После удаления журнала старый запрос не запускается как новая операция; проверяются окно replay и актуальность контекста звонка. Политика резервных копий отдельно обеспечивает сроки для удаляемых связей и аудитов.

Операционные идентификаторы отделяются от аудита и не объявляются анонимными. Их ретенция не продлевается автоматически каждым повтором. Сохранение текстов заявок/SMS и персональных данных звонящих по-прежнему не разрешено. Надёжная доставка SMS после любого сбоя и неограниченная дедупликация после удаления журнала не гарантируются.

## 11. Локальная разработка и подключение провайдеров

Разработка сценариев не требует немедленной покупки номера: сначала нужны Node.js/TypeScript, локальный PostgreSQL, тестовые мастерские/услуги и адаптеры с фиктивными ответами. Проверки авторизации и Zod работают и в тестовом режиме; секреты не отключаются ради удобства.

Node.js уже установлен. Docker не обязателен: PostgreSQL можно установить как обычную системную службу, создать отдельную БД и пользователя приложения и подключить через `DATABASE_URL`. Drizzle и миграции не зависят от способа запуска PostgreSQL.

Для проверки настоящего Calendar понадобятся проект Google с Calendar API, служебный аккаунт, его учётные данные вне репозитория и тестовый календарь, вручную открытый этому аккаунту. Для настоящих SMS — аккаунт SMSAPI, токен, получатель и настроенный отправитель. Для реального звонка — отдельный номер мастерской, SIP trunk, агент ElevenLabs и доступный извне HTTPS endpoint; параметры событий проверяются на реальном тесте. Туннель нужен для входящих запросов в локальную среду, не для модульных тестов.

Northflank и Neon подключаются позднее. При переходе нужно отдельно проверить управление секретами, миграции Drizzle, соединения с PostgreSQL и выполнение политики удаления; их наличие пока не предполагается.

Критические локальные сценарии: успешная запись, конфликт слота, повтор tool call, Relay, неизвестная услуга → диагностика, скрытый Caller ID, отказ календаря и неопределённый результат создания, ошибка SMS без повторной брони, отказ нового AI-разговора после 40 минут, сохранение настроек и счётчиков после рестарта, отсутствие персональных данных звонящих в БД/логах и удаление аудитов по сроку.

Дополнительные обязательные проверки восстановления и ретенции:

- Два параллельных допуска при последнем доступном резерве; повтор допуска без продления TTL; завершение после истечения резерва; повтор завершения без повторного списания; завершение без допуска; отклонение событий вне окна replay.
- Два разных бронирования одной мастерской при отпущенной транзакционной блокировке; падение после коммита `PENDING`, после успешного Google `insert` и до фиксации результата; зависший старый владелец после истечения lease. Новый запрос не обходит занятый шлюз.
- `404` при ещё выполняющемся `insert`, `409` при повторе с тем же ID, неоднозначный `5xx`, тайм-аут самой сверки; ни один сценарий не генерирует новый ID для той же операции.
- Повторно выданный токен того же слота, истёкший токен завершённой операции; отсутствие времени визита и полного HTTP-ответа в `result_payload`; отдельная неопределённая SMS-операция без повторной брони.
- Поздний `call-ended` с исходным `call_ended_at`, аудит после завершения, отсутствие завершения, удалённая семидневная связь, запрет чтения просроченного аудита до физической очистки, очистка после простоя и координация нескольких воркеров.

## 12. Спецификация HTTP-контрактов API

Все эндпоинты принимают и отдают `application/json`. Ошибки валидации Zod возвращают `400 Bad Request`, ошибки авторизации — `401 Unauthorized`.

### 12.1. Служебный и Административный API

Защита: заголовок `x-admin-secret` (сравнение через `crypto.timingSafeEqual`).

- `GET /health` — проверка доступности сервиса и подключения к PostgreSQL (без авторизации).
- `POST /admin/tenants` — создание мастерской + автоматическая инициализация `pilot_usage` (14 дней, 40 минут).
- `PATCH /admin/tenants/:id` — обновление режима (`CALENDAR` / `RELAY`), расписания, интеграций (`zadarma_number`, `elevenlabs_agent_id`, `google_calendar_id`, `sms_recipient_phone`).
- `POST /admin/tenants/:id/services` — добавление/обновление списка услуг мастерской.
- `GET /admin/tenants/:id/status` — получение настроек мастерской и текущего остатка минут/дней пилота (без персональных данных).

### 12.2. События телефонии и AI (Webhooks)

Защита: `x-webhook-secret` (локально; в продакшене заменяется на серверную верификацию провайдера через `ProviderAuthAdapter`).

- `POST /webhooks/call-admission` — проверка допуска до старта сессии ElevenLabs (в транзакции с блокировкой строки `pilot_usage`).
    - **Request (локальный нормализованный контракт):** `{ "called_number": "+48...", "agent_id": "...", "external_call_id": "...", "call_started_at": "ISO" }`. Провайдер и временные метки в реальной интеграции определяются проверенным адаптером, а не LLM.
    - **Logic:** проверяет доверенный контекст, возраст события, активность мастерской, отсутствие завершённого/истёкшего допуска, `now() < pilot_usage.expires_at`, отсутствие блокировки и `minutes_used + SUM(активных резервов) + TEST_RESERVE_MINUTES <= minutes_limit`. Создаёт индивидуальный резерв на 10 минут и `audit_session_id`, фиксирует решение на 7 дней. Повтор активного допуска возвращает прежнее решение без нового резерва/продления; закрытый или истёкший допуск не разрешает повторный запуск.
    - **Response (`200`):** `{ "allowed": true, "tenant_id": "uuid", "mode": "CALENDAR" | "RELAY", "call_id": "internal-uuid" }` или `{ "allowed": false, "reason": "LIMIT_EXCEEDED" | "PILOT_EXPIRED" | "TENANT_NOT_FOUND" | "TENANT_INACTIVE" | "TENANT_BLOCKED" | "CALL_CLOSED" | "ADMISSION_EXPIRED" | "EVENT_TOO_OLD" | "TOO_EARLY" }`. Локально `TOO_EARLY` до десяти секунд содержит `retry_after_seconds`; реальный допуск/ожидание должен обеспечить маршрут телефонии до AI.
- `POST /webhooks/call-ended` — фиксация расхода минут по завершении разговора (идемпотентно по `external_call_id`).
    - **Request (локальный нормализованный контракт):** `{ "external_call_id": "...", "called_number": "+48...", "agent_id": "...", "call_started_at": "ISO", "call_ended_at": "ISO", "ai_seconds": 85 }`. Проверяются порядок/достоверность времён, неотрицательная длительность и допустимый возраст события; время получения не подменяет завершение.
    - **Logic:** в одной транзакции под блокировкой `pilot_usage` находит запись по `(tenant_id, provider, external_call_id)`, закрывает только её резерв и при `usage_accounted = false` прибавляет `Math.ceil(ai_seconds / 60)` (0 при нулевой длительности). Фиксирует `usage_accounted = true`, проверенное `call_ended_at` и обновляет ещё доступные аудиты сессии на `call_ended_at + 30 days`. При достижении лимита блокирует новые допуски. Истечение десятиминутного резерва не мешает списанию в пределах семидневного окна. Отсутствие записи допуска обрабатывается по разделу 8; слишком старые события не списываются автоматически.

### 12.3. Инструменты голосового агента (ElevenLabs Tools)

Защита: `x-tool-secret`.

**Доверенный контекст звонка:** модель **не передаёт** `called_number`, `agent_id` и `call_id` в JSON-аргументах тулзов. Контекст извлекается слоем `CallContextResolver`:

- В локальном/тестовом режиме (`NODE_ENV !== 'production'`): из явных тестовых заголовков `x-test-called-number`, `x-test-agent-id`, `x-test-call-id` и опционального `x-test-caller-id` (E.164). При отсутствии `x-test-caller-id` звонок считается со скрытым Caller ID.
- В продакшене: интерфейс `CallContextResolver` заменяется на серверную привязку сессии провайдера (после проверки реальных контрактов ElevenLabs/Zadarma).

- `POST /tools/check-availability`
    - **Request (от LLM):** `{ "service_id": "uuid", "date_query": "jutro po południu" }`
    - **Response (`200`):**
        - При `CALENDAR`: `{ "status": "SLOTS_AVAILABLE", "slots": [{ "slot_id": "hmac_token", "start_at": "ISO", "end_at": "ISO" }] }` (или `"NO_SLOTS"`). Расчёт опирается на `tenants.scheduling_config` (тестовые настройки шага и горизонта).
        - При `RELAY` или сбое календаря: `{ "status": "FALLBACK_RELAY", "reason": "CALENDAR_UNAVAILABLE" | "RELAY_MODE" }`.
- `POST /tools/book-slot`
    - **Request (от LLM):** `{ "slot_id": "hmac_token", "client_name": "...", "client_phone": "+48...", "car_model": "...", "problem_description": "..." }` (если в доверенном контексте есть `caller_id`, backend использует его вместо `client_phone`, не давая модели подменить номер; если `caller_id` скрыт — `client_phone` помечается как непроверенный).
    - **Logic:** двухтранзакционный протокол, постоянный шлюз мастерской и сверка `PENDING`/`UNCERTAIN` по разделу 5. Внешний запрос выполняется только после коммита намерения. Ни повтор, ни истечение lease не разрешают обойти незавершённую операцию; SMS имеет отдельный результат. Времена визита в ответе не копируются в `result_payload`.
    - **Response (`200`):** `{ "status": "BOOKED" | "SLOT_CONFLICT" | "CALENDAR_ERROR_USE_RELAY" | "PENDING_VERIFICATION", ... }`
- `POST /tools/create-relay`
    - **Request (от LLM):** `{ "client_name": "...", "client_phone": "+48...", "car_model": "...", "problem_description": "...", "preferred_time": "..." }` (логика верификации телефона аналогична `book-slot`).
    - **Response (`200`):** `{ "status": "RELAY_SENT" }`, `{ "status": "RELAY_FAILED" }` или `{ "status": "PENDING_VERIFICATION" }` при неизвестном результате передачи. `RELAY_SENT` означает подтверждённое принятие SMSAPI, не доставку сотруднику.
