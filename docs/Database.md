# PostgreSQL Gloso — локальный MVP

Источники истины: [`Architecture.md`](Architecture.md), [`../backend/src/db/schema.ts`](../backend/src/db/schema.ts), SQL-миграции в [`../backend/drizzle/`](../backend/drizzle/). ORM — Drizzle, PostgreSQL 16+. Все временные метки — `timestamptz`, приложение возвращает ISO 8601. Рабочая зона расписания — `Europe/Warsaw`.

## Допустимые данные

Хранятся конфигурация мастерских, услуги, расписания, пилот, расход, резервы звонков, технические операции и зашифрованный аудит. **Не хранятся** имя/телефон звонящего, автомобиль, описание проблемы, желаемое время/время визита, текст заявки/SMS, полный HTTP-ответ, токен слота, сырой webhook, аудио или транскрипция.

Номера мастерской и сотрудника — конфигурация. Внешние ID звонка и внутренние корреляционные идентификаторы — разрешённое краткоживущее операционное состояние, не обещание анонимности.

## Таблицы

### `tenants`

- `id` UUID PK, `name`, `mode` (`CALENDAR`/`RELAY`), `is_active`.
- Уникальные `zadarma_number` и `elevenlabs_agent_id`.
- `google_calendar_id` nullable; CHECK требует календарь для `CALENDAR`.
- `sms_recipient_phone`, `work_hours` JSONB, `scheduling_config` JSONB.
- `created_at`, `updated_at`.

Расписание — дни `1`–`7`, массивы `{start, end}` в `HH:mm`. Отсутствующий день закрыт. Приложение проверяет непересечение интервалов и их принадлежность одному дню. Конфигурация поиска — тестовые шаг, горизонт и минимальная задержка. Оба JSON-поля валидируются Zod, не содержат заявок.

### `services`

- `id` UUID PK, `tenant_id` FK, `name`, `duration_minutes`, `is_diagnostic`.
- CHECK длительности 5–1440 минут.
- Индекс по мастерской, частичный unique-индекс одной диагностической услуги.

Административный API обновляет список без удаления пропущенных услуг. Чужой ID не может быть обновлён. Каскадное удаление мастерской не предоставлено: без явной процедуры нельзя уничтожить её журнал и обходить восстановление.

### `pilot_usage`

- `tenant_id` PK/FK (1:1), `activated_at`, `expires_at`.
- `minutes_limit` (40), `minutes_used` (0), `is_blocked`.
- CHECK неотрицательности лимита и расхода.

Пилот активируется при создании мастерской на 14 календарных дней. Общего изменяемого `minutes_reserved` нет: это сумма индивидуальных активных резервов. Реальный расход может превысить лимит, поскольку уже допущенный разговор не прерывается.

### `active_call_reservations`

- Составной PK `(tenant_id, provider, external_call_id)`.
- `call_id` — отдельный случайный внутренний UUID с UNIQUE, возвращается локальным допуском. Не совпадает с ID провайдера или аудит-сессии.
- `audit_session_id` — случайный UUID для связи с аудитом.
- `status`: `ACTIVE`, `CLOSED`, `REJECTED`; `admission_reason`.
- `reserved_minutes`, `reservation_expires_at` (nullable без резерва).
- `call_started_at`, `call_ended_at`, `usage_accounted`.
- `booking_operation_key` — техническая связь с операцией бронирования этого звонка: блокирует Relay при неизвестном исходе и вторую независимую бронь после успеха. Не содержит времени/данных визита.
- `created_at`, `expires_at` (7 дней от создания).
- Индексы активных резервов и очистки; CHECK неотрицательного резерва.

Десятиминутный срок резерва — не срок хранения строки: строка остаётся для позднего завершения и дедупликации. Статус `ACTIVE` с истёкшим резервом не входит в сумму, но не обрывает уже начатый разговор. Для автоматических событий проверяется возраст от исходного `call_started_at` (до 7 дней); новое время webhook не омолаживает звонок.

### `processed_events`

- `idempotency_key` text PK: непрозрачный серверный HMAC, не сырой ID звонка.
- `tenant_id` FK, `event_type` (`BOOKING`, `BOOKING_SMS`, `RELAY_SMS`).
- `status`: `PENDING`, `COMPLETED`, `UNCERTAIN`, `FAILED`.
- `external_ref`: ID события Google или технический ID SMS.
- `calendar_ref`: календарь исходной операции; изменение конфигурации не меняет место сверки.
- `parent_operation_key`: связь уведомления с логической операцией.
- `result_payload` JSONB: только `status`, `error_code`, `sms_status`; проверяется строгой схемой. Нет `start_at`, `end_at` и содержимого визита.
- `created_at`, `updated_at`, `expires_at` (7 дней от создания).
- Индексы срока и незавершённых операций мастерской.

Ключ бронирования зависит от стабильных полей подписанного слота, но не от его срока/строки токена; в БД сохраняется только HMAC. Секреты HMAC находятся вне БД. Для Relay ключ стабилен в рамках одного звонка, без хеша персонального содержимого. SMS журналируется отдельно; подтверждённую передачу нельзя повторять из-за ошибки уведомления или повторного tool call.

### `tenant_booking_gates`

- `tenant_id` PK/FK (1:1), `state`: `IDLE`, `BUSY`, `RECOVERY_REQUIRED`.
- `operation_key`, `owner_token`, `owner_version`, `lease_expires_at`, `updated_at`.
- CHECK согласованности состояния/ссылки операции.

Шлюз сериализует записи одной мастерской между процессами, включая время вне SQL-транзакции. Lease позволяет выбрать восстановителя, но не является fencing-механизмом Google и не разрешает новую бронь автоматически. Нет времени визита и теневого календаря.

### `audit_logs`

- `id` UUID PK, `tenant_id` FK, `audit_session_id` UUID.
- `action`: разрешённое техническое действие.
- `encrypted_meta`: AES-256-GCM, `iv:authTag:ciphertext` в hex. Разрешены только `service_id`, `mode`, `provider_status`, `ai_seconds`.
- `created_at`, `expires_at`; индексы срока и аудит-сессии.
- Нет FK на строку звонка: удаление семидневной связи не удаляет аудит.

Внешние/внутренние ID звонка и время визита не записываются в encrypted JSON. Связь с внешним звонком доступна только через семидневную операционную строку. После удаления связи возможна косвенная корреляция; полная анонимность не гарантируется.

## Блокировки и атомарность

1. Все изменения состояния мастерской берут короткий `pg_advisory_xact_lock(hashtext(tenant_id))`.
2. Допуск/списание дополнительно блокируют `pilot_usage FOR UPDATE`; запись аудита/завершение согласуются на строке звонка.
3. Внешние сетевые вызовы не выполняются внутри SQL-транзакции.
4. Перед Calendar insert фиксируются намерение `PENDING`, исходный календарь, внешний ID и шлюз. После подтверждённого результата отдельная транзакция обновляет журнал/шлюз с проверкой владельца/версии.
5. Неизвестный результат сверяется по прежнему ID; `404`, тайм-аут и произвольный `5xx` не снимают шлюз автоматически. Локальный MVP консервативно не делает повторный insert после неизвестного исхода без доказательства завершения старого писателя.
6. Восстановление может прочитать внешнее событие без персонального содержимого в БД. Потерянное тело заявки из БД восстановить нельзя.

## Ретенция

| Данные | Срок/поведение |
| --- | --- |
| Резерв минут | 600 секунд по тестовой настройке; истечение учитывается запросом немедленно |
| Строка звонка и связь ID | 7 дней от создания, без продления повтором |
| Журнал внешних операций | 7 дней от создания, без продления повтором |
| Аудит | 30 дней от проверенного завершения; пока оно неизвестно — от создания |
| Конфигурация, услуги, пилот/расход | Не удаляются автоматически по сроку аудита |
| Минимальный запрет `RECOVERY_REQUIRED` | До ручной сверки, без удалённых внешних ID и связи со звонком |

Любое чтение аудита фильтрует `expires_at > now`. Поздний webhook использует реальный `call_ended_at`, а не время доставки; при удалённой связи точное обновление срока уже невозможно. Воркер запускается перед обслуживанием HTTP и раз в час, координируется через `pg_try_advisory_xact_lock`. Физическое удаление может задерживаться до часа или до запуска после простоя; истёкшая связь при этом не используется.

Перед удалением незавершённого журнала шлюз переводится в `RECOVERY_REQUIRED`, ссылка операции и токен владельца убираются, версия меняется. Старый писатель не сможет завершить операцию в БД по прежней версии. Однако это не отменяет запрос у внешнего провайдера: ручное снятие блокировки требует остановки старых писателей и внешней проверки.

Резервные копии в локальном MVP не настраиваются. Перед реальным размещением обязательны отдельная политика удаления копий/связей и очистка просроченных данных до открытия восстановленной БД для приложения. Семидневная дедупликация не является бессрочной защитой от replay.

## Команды

Из `backend/`: `npm run db:generate` — генерация миграции, `npm run db:migrate` — применение, `npm run db:seed` — фиктивные мастерские. Миграции не запускаются автоматически сервером. Тесты используют отдельный временный PostgreSQL и никогда не берут рабочий `DATABASE_URL` по умолчанию.
