# Gloso backend — локальный MVP

Node.js + TypeScript + Express, Zod, PostgreSQL + Drizzle. Источник требований — [`../docs/Architecture.md`](../docs/Architecture.md).

**Это локальный mock-режим, не подключённый к Google, SMSAPI, Zadarma или ElevenLabs.** Ни звонки, ни настоящие SMS не выполняются. Ответы помечены `X-Gloso-Mode: local-mock`. Production-запуск заблокирован до реализации проверенной аутентификации и привязки сессий провайдеров.

## Требования

- Node.js 22+ (проверено на Node.js 24).
- PostgreSQL 16+ и отдельные БД/пользователь приложения. Docker не обязателен.
- Доступ npm к зависимостям при первой установке.

## Запуск

Все команды ниже выполняются из `backend/`.

```bash
npm ci
npm run env:init
```

Команда создаёт `.env` с независимыми случайными секретами, правами `0600` и **не перезаписывает** существующий файл. Отредактируйте `DATABASE_URL`: укажите отдельную локальную БД и её учётные данные. Значение `gloso:change-me` в шаблоне — заглушка, роль/БД автоматически не создаются. Не используйте учётные данные рабочего окружения.

```bash
npm run db:migrate
npm run db:seed
npm run dev
```

Сервер по умолчанию слушает **только `127.0.0.1:3000`**. `GET /health` проверяет соединение с PostgreSQL. Миграции выполняются явно, не при каждом старте. Очистка/восстановление выполняются перед началом обслуживания запросов, затем раз в час.

Seed повторяемый: существующие мастерские с `mock-agent-1`/`mock-agent-2` не меняются. Новые мастерские получают пилот 14 календарных дней в `Europe/Warsaw`, 40 минут и фиктивные услуги. Seed выводит их ID и ID услуг; это не данные звонящих.

Сборка и запуск без watch:

```bash
npm run build
npm start
```

## Проверки

```bash
npm run typecheck
npm run lint
npm test
npm run test:integration
npm run build
npm audit
```

`npm test` не требует БД. Интеграционный runner **не использует `DATABASE_URL`**: создаёт собственный временный кластер настоящего PostgreSQL в `/tmp/opencode/gloso-pg-*`, запускает тесты и удаляет только этот собственный каталог после остановки. Системные роли и базы не меняются. Нужны `initdb`/`pg_ctl`, запускаемые обычным пользователем (не root).

Если бинарные файлы не находятся через `pg_config`, задайте `PG_BIN`, например `/usr/lib/postgresql/16/bin`. При отсутствии `/tmp/opencode` создайте его или укажите существующий каталог `GLOSO_TEST_TMP`.

Альтернатива — `TEST_DATABASE_URL` на **специальную тестовую БД с именем, оканчивающимся `_test`**. Тесты удаляют все данные семи таблиц в этой БД. Нельзя указывать БД приложения, даже если её имя подходит. Runner использует этот URL только по явному указанию.

Интеграционные тесты проверяют настоящие транзакции/блокировки, несколько процессов бэкенда и `SIGKILL` между созданием события внешним тестовым провайдером и фиксацией результата в PostgreSQL. Провайдер в этих тестах живёт отдельно и переживает падение бэкенда.

## API и демонстрация

Полные локальные контракты: [`API.md`](API.md). Последовательность:

1. Создать мастерскую через `/admin/tenants` или использовать seed.
2. Добавить услуги; получить ID диагностической услуги через административный status.
3. Отправить `/webhooks/call-admission` с отдельным `external_call_id` и исходным `call_started_at` минимум 10 секунд назад.
4. Сохранить возвращённый **внутренний `call_id`**, не подменять его ID провайдера.
5. Вызвать `/tools/check-availability` с тестовым контекстом в заголовках.
6. Выбрать `slot_id`, вызвать `/tools/book-slot`. Либо вызвать `/tools/create-relay` для Relay-заявки.
7. Отправить `/webhooks/call-ended` с тем же внешним ID, исходным временем, фактическим временем завершения и числом секунд AI.
8. Повторить команды: новая бронь/SMS и повторное списание появляться не должны.

Параметры `slot_step_minutes=30`, `booking_horizon_days=14`, `min_lead_time_minutes=60`, резерв 1 минута и TTL 600 секунд — **тестовые**, не окончательные обещания клиенту. Ограничение звонка 3–4 минутами не реализовано. Локальная проверка десяти секунд не заменяет реальную маршрутизацию SIP до подключения AI.

## Данные и ограничения

- PostgreSQL содержит конфигурацию, расход, индивидуальные резервы и технические операции. Нет таблиц клиентов, заявок, персональных визитов и очереди с текстом SMS.
- Имена, номера звонящих, автомобиль, описание проблемы, время визита, тело SMS, `slot_id`, сырые webhook, аудио и транскрипции не сохраняются в БД/логах.
- Номера мастерской/получателя SMS — разрешённая конфигурация. Внешний ID звонка и его связь с аудитом — ограниченное семью днями операционное состояние.
- Аудит шифруется AES-256-GCM и содержит только разрешённые поля. UUID и удаление прямой связи не гарантируют полной анонимности.
- Нет HTTP-архива аудитов, звонков или клиентов.
- Конфигурация и операционное состояние переживают рестарт. **Обычный mock Calendar/SMS хранится в памяти и после рестарта теряется**: это не долговечная внешняя система. При неизвестном исходе бэкенд сохраняет блокировку, не создаёт событие заново наугад. Отдельный переживающий рестарт провайдер используется в тестах.
- Нет гарантии доставки SMS после любого сбоя: если неизвестно, принял ли провайдер сообщение, слепой повтор запрещён.
- Для реальных адаптеров ещё нужны проверенные ответы/подписи, правила retry/reconciliation и настройки удаления у провайдеров. Резервные копии/их ретенция пока не развёрнуты и автоматически не управляются.

## Восстановление и ручная сверка

Журнал намерения фиксируется до внешнего запроса. `PENDING` и `UNCERTAIN` сверяются по прежнему ID события в исходном календаре. `404` и истёкший lease **не освобождают** мастерскую, если старый запрос мог ещё выполняться. Без доказанного исхода новые Calendar-бронирования ждут; повторная передача того же обращения через Relay тоже блокируется.

При истечении семидневной ретенции неразрешённая мастерская переходит в `RECOVERY_REQUIRED`. Журнал/внешние ID удаляются, минимальное состояние запрета остаётся. Автоматического принудительного снятия нет.

Для ручного снятия:

1. Остановить все старые/зависшие экземпляры, способные выполнять записи. Не считать один истёкший lease доказательством их остановки.
2. Проверить календарь и разрешить неопределённые/конфликтующие события вне системы. После удаления журнала его внешний ID восстановить из PostgreSQL уже нельзя.
3. Запустить обслуживающий экземпляр без старых писателей.
4. Вызвать `POST /admin/tenants/:id/recovery-release` с административным секретом и `{ "writers_stopped": true, "external_calendar_verified": true }`.

Эндпоинт разрешён только для `RECOVERY_REQUIRED`, это доверенное подтверждение оператора, не автоматическое доказательство состояния Google. Для `BUSY` не предусмотрено опасной кнопки «сбросить lock».

## Дальнейшее подключение

Порядок: Google Calendar → SMSAPI → Zadarma/ElevenLabs → размещение Northflank/Neon. Нельзя просто установить `NODE_ENV=production` и считать тестовые заголовки доверенными. Нужны реальная привязка сессий, допуск до AI, проверка задержки, Caller ID и учёта длительности, политика резервных копий и ретенции у внешних провайдеров.
