# HTTP API локального MVP

Все тела — `application/json`, поля без неизвестных ключей. Даты событий — ISO 8601 с часовым поясом, телефоны — E.164. Ответы помечены `X-Gloso-Mode: local-mock` и не подтверждают работу реальных интеграций.

## Авторизация

| Маршрут | Заголовок |
| --- | --- |
| `/health` | Без авторизации |
| `/admin/*` | `x-admin-secret` |
| `/webhooks/*` | `x-webhook-secret` |
| `/tools/*` | `x-tool-secret` плюс тестовый контекст |

Тестовый контекст: `x-test-called-number`, `x-test-agent-id`, `x-test-call-id` (UUID, возвращённый допуском), опционально `x-test-caller-id`. Он принимается только локально; модель не передаёт контекст в JSON. Отсутствующий Caller ID означает скрытый номер. Подмена внутреннего call ID на чужую мастерскую отклоняется.

Наличие Caller ID определяет источник телефона, но не подтверждает владение им. При наличии доверенного Caller ID backend использует его вместо `client_phone`. Без Caller ID для операции обязателен продиктованный `client_phone`, помечаемый непроверенным.

## Административные маршруты

### `GET /health`

`200 { "status": "ok", "mode": "local-mock" }`; при недоступности БД — `503 { "status": "unavailable" }`.

### `POST /admin/tenants`

```json
{
  "name": "TEST — warsztat",
  "mode": "CALENDAR",
  "is_active": true,
  "zadarma_number": "+48220000001",
  "elevenlabs_agent_id": "mock-agent-1",
  "google_calendar_id": "mock-calendar-1",
  "sms_recipient_phone": "+48500000000",
  "work_hours": { "1": [{ "start": "08:00", "end": "17:00" }] },
  "scheduling_config": {
    "slot_step_minutes": 30,
    "booking_horizon_days": 14,
    "min_lead_time_minutes": 60
  }
}
```

`201` возвращает конфигурацию и `id`. Пилот активируется сразу при создании: 14 календарных дней в Warsaw, 40 минут. `is_active` по умолчанию true. Режим `RELAY` допускает `google_calendar_id: null`. Календарный режим требует ID календаря.

Дни расписания: `1` — понедельник, `7` — воскресенье; отсутствующий день закрыт. До четырёх непересекающихся интервалов на день, внутри одного календарного дня. Расписания через полночь в MVP не поддерживаются. Время `HH:mm`, конец строго позже начала. Пропущенный `scheduling_config` получает явно тестовые значения из примера.

### `PATCH /admin/tenants/:id`

Частичное обновление тех же полей (хотя бы одно). JSON-поля заменяются целиком. Изменение режима/календаря при занятом шлюзе отклоняется. Полей прямого произвольного изменения счётчиков или платёжных состояний нет.

### `POST /admin/tenants/:id/services`

```json
{
  "services": [
    { "name": "Diagnostyka TEST", "duration_minutes": 60, "is_diagnostic": true },
    { "id": "00000000-0000-4000-8000-000000000001", "name": "Обновлённая услуга", "duration_minutes": 90, "is_diagnostic": false }
  ]
}
```

Без `id` услуга создаётся; с `id` обновляется существующая услуга **этой мастерской**. Оставшиеся услуги не удаляются. Повторное создание без ID не идемпотентно. Не более одной диагностической услуги на мастерскую; длительность 5–1440 минут. `200 { "services": [...] }`.

### `GET /admin/tenants/:id/status`

Конфигурация, услуги, `booking_gate` и `pilot`: `activated_at`, `expires_at`, `minutes_limit`, `minutes_used`, `minutes_reserved` (вычисляемая сумма), `minutes_available` (не ниже нуля), `is_blocked`, `days_remaining` (информационное округление оставшихся часов вверх до суток). Источник истины срока — `expires_at`, не округлённое число дней.

### `POST /admin/tenants/:id/recovery-release`

```json
{ "writers_stopped": true, "external_calendar_verified": true }
```

Только `RECOVERY_REQUIRED` после ручной процедуры из README. `200 { "status": "RELEASED" }`. Эти флаги — ответственность оператора, не выполненная бэкендом проверка Google.

## События звонка

Это **внутренние локальные контракты**, не заявленные реальные форматы Zadarma/ElevenLabs. Адаптер провайдера в будущем должен проверять подпись, namespace и достоверность меток времени.

### `POST /webhooks/call-admission`

```json
{
  "called_number": "+48220000001",
  "agent_id": "mock-agent-1",
  "external_call_id": "unique-provider-call-1",
  "call_started_at": "2026-11-19T08:00:00Z"
}
```

Используйте **актуальное исходное время**, не фиксированную дату примера. В локальном режиме до десяти секунд возвращается `allowed: false`, `reason: "TOO_EARLY"`, `retry_after_seconds`; AI запускать нельзя. Допуск затем возвращает:

```json
{ "allowed": true, "tenant_id": "uuid", "mode": "CALENDAR", "call_id": "internal-uuid" }
```

Отказ: `allowed: false`, `reason` — `LIMIT_EXCEEDED`, `PILOT_EXPIRED`, `TENANT_NOT_FOUND`, `TENANT_INACTIVE`, `TENANT_BLOCKED`, `CALL_CLOSED`, `ADMISSION_EXPIRED`, `EVENT_TOO_OLD` или `TOO_EARLY`.

Повтор сохраняет исходный ID и TTL, а не создаёт новый разговор. Оркестратор телефонии также обязан дедуплицировать запуск AI; ответ `allowed: true` сам по себе не запускает ElevenLabs. Тот же ID с другим исходным временем — `409 CALL_CONTEXT_MISMATCH`.

### `POST /webhooks/call-ended`

Поля допуска плюс `call_ended_at` и неотрицательный целочисленный `ai_seconds`. Завершение не позже текущего времени, не раньше начала; AI-секунды не превышают общую длительность. Автоматическое окно обработки — до 7 дней от `call_started_at`.

`200`: `ACCOUNTED` с `minutes_charged`, `ALREADY_PROCESSED`, `EVENT_TOO_OLD` или `TENANT_NOT_FOUND`. Успешное списание равно `ceil(ai_seconds / 60)`, ноль секунд даёт ноль минут. Позднее завершение после TTL резерва всё ещё учитывается в пределах окна. Неполученное завершение освобождает только резерв, но не доказывает нулевой расход.

## Инструменты

### `POST /tools/check-availability`

```json
{ "service_id": "uuid", "date_query": "jutro po południu" }
```

Неизвестная услуга обозначается пропущенным или null `service_id`, тогда выбирается настроенная диагностика. Произвольный отсутствующий UUID или ID чужой услуги отклоняется, а не подменяется диагностикой.

Поддерживаются `dzisiaj`/`dziś`, `jutro`, `pojutrze`, опционально `rano` (08–12), `po południu` (12–18), `wieczorem` (18–24), а также `YYYY-MM-DD` и `YYYY-MM-DD HH:mm`. Это ограниченные тестовые трактовки, не универсальное понимание естественного языка. Неоднозначное или несуществующее местное время требует уточнения.

Результаты:

- `SLOTS_AVAILABLE`, `service_id`, до пяти `slots: [{ slot_id, start_at, end_at }]`.
- `NO_SLOTS`, пустой список.
- `SERVICE_CLARIFICATION_REQUIRED` — нет диагностической услуги.
- `DATE_CLARIFICATION_REQUIRED` — нужна точная дата/время.
- `FALLBACK_RELAY`, `reason: RELAY_MODE | CALENDAR_UNAVAILABLE`.

### `POST /tools/book-slot`

```json
{
  "slot_id": "signed-token",
  "client_name": "Test caller",
  "client_phone": "+48500000001",
  "car_model": "Test car",
  "problem_description": "Test problem"
}
```

Телефон необязателен только при наличии доверенного Caller ID. Результаты:

- `BOOKED`, `start_at`, `end_at`, `sms_sent`, `sms_status: ACCEPTED | FAILED | PENDING_VERIFICATION`.
- `SLOT_CONFLICT` — предложить другой слот.
- `CALENDAR_ERROR_USE_RELAY` — определённый отказ до создания либо подтверждённое отсутствие эффекта.
- `PENDING_VERIFICATION` — исход неизвестен, шлюз занят или требуется ручная сверка. Не подтверждать визит и не передавать то же обращение как независимый Relay.

Один звонок не может начать вторую независимую бронь после успешной или ещё неопределённой первой (`409 BOOKING_ALREADY_STARTED`). После определённого конфликта можно выбрать другой слот. Завершённая операция повторяется без создания события. Истёкший подписанный токен допускает только возврат уже существующего результата, не новое создание.

### `POST /tools/create-relay`

Те же клиентские поля без `slot_id`, плюс обязательное `preferred_time` (строка, до 150 символов). Один логический Relay на звонок: повтор не отправляет изменённую заявку заново.

- `RELAY_SENT` — SMS подтверждённо принято mock-провайдером, не подтверждение доставки.
- `RELAY_FAILED` — определённый отказ передачи.
- `PENDING_VERIFICATION` — результат неизвестен или есть незавершённая Calendar-операция этого звонка.

Созданная Calendar-бронь не дублируется Relay-заявкой (`409 BOOKING_ALREADY_CREATED`).

## Ошибки

Формат: `{ "error": { "code": "..." } }`; валидация может дополнительно вернуть имена полей, но не полученные значения.

| HTTP | Значение |
| --- | --- |
| 400 | Валидация, JSON, неверный/истёкший слот, некорректные времена |
| 401 | Секрет или контекст звонка отсутствует/неверен |
| 403 | Подписанный слот другой мастерской |
| 404 | Не найдена мастерская/услуга/маршрут |
| 409 | Конфигурационный конфликт или несовместимое состояние операции |
| 413 | Тело больше 16 KB |
| 415 | Не `application/json` |
| 500 | Внутренняя ошибка, без SQL/stack/персональных данных |
| 503 | Проверка доступности БД не прошла |

Текстовые поля ограничены: имя 100, автомобиль 150, описание 1000 символов. Все тестовые имена/телефоны выше фиктивные; не используйте реальные данные при проверке локальных mock-сценариев.
